# 미션 실행 및 장비 통신 설계 초안

첫 구현은 **저장된 미션 준비 → 테스트 장비의 응답 반영 → 상태 조회 → 준비 취소**다. 준비 시점에 미션 버전과 내용을 회차에 고정한다. 같은 미션을 수정하거나 다시 실행해도 앞선 회차의 내용과 결과는 유지한다.

현재 서버에는 계정·정원·장비 API가 있다. 미션 저장 API는 이 작업의 선행 계약이며, 초기 구현은 합의한 형태의 테스트 미션을 사용한다. FE에는 이미 준비·장비 수락·시작을 표현하는 시뮬레이션이 있다. [백엔드 구현 현황](../BE/README.md#아직-구현하지-않은-것) · [FE 상태 모델](../FE/src/types/control.ts)

## API

### 첫 PR

| 요청 | 입력 | 응답과 동작 |
| --- | --- | --- |
| `POST /api/me/missions/{missionId}/runs` | `missionVersion`, `Idempotency-Key` 헤더 | `202`. 회차를 `PREPARING`으로 만들고 `PREPARE` 명령을 저장한다. 같은 요청을 다시 보내면 기존 회차를 반환한다. |
| `GET /api/me/runs/{runId}` | 회차 ID | `200`. 회차, 최근 명령과 상태, 마지막 장비 보고 시각, 거부·무응답 사유를 반환한다. |
| `POST /api/me/runs/{runId}/cancel` | `Idempotency-Key` 헤더 | `202`. 시작 전의 준비 회차에 `CANCEL_PREPARE`를 요청한다. 같은 취소 요청을 반복하면 기존 명령 결과를 반환한다. |

요청을 저장한 뒤 `202`로 응답하며, 화면은 응답 본문의 `runId`로 상태를 조회한다. 미션은 로그인한 사용자의 정원에 속해야 하며, 준비 시 정원 활성 상태와 배정 장비를 확인한다. 미션 버전이 바뀌었거나 장비에 미해결 회차가 있거나 현재 상태에서 허용되지 않는 요청이면 `409`를 반환한다. 다른 운영자의 회차는 조회·조작할 수 없다. [HTTP 202의 의미](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)

준비 요청 직후 상태 조회에서 볼 수 있는 응답 예시다.

```json
{
  "runId": 42,
  "missionId": 17,
  "missionVersion": 3,
  "deviceId": "ROVEN-01",
  "state": "PREPARING",
  "latestCommand": { "id": "cmd-42-1", "type": "PREPARE", "status": "QUEUED" },
  "lastReportAt": null,
  "reason": null
}
```

### 후속 계약

| 요청 | 동작 |
| --- | --- |
| `POST /api/me/runs/{runId}/start` | 준비 완료 회차의 `START` 명령을 기록한다. 미션 버전과 현재 장비 배정을 다시 확인한다. 준비 이후 변경됐다면 준비를 취소하고 최신 버전으로 다시 준비한다. |
| `POST /api/me/runs/{runId}/pause` | 실행 중 회차에 `PAUSE`를 요청한다. |
| `POST /api/me/runs/{runId}/stop` | 시작을 요청한 회차에 `STOP`을 요청한다. |
| 장비 보고 수신 | 장비에서 오는 명령 수신 확인, 상태, 결과를 같은 보고 처리기로 전달한다. 실제 통신 경로와 장비 인증 방식은 장비팀과 정한다. |

사용자 명령 API는 접수 후 `202`를 반환한다. 첫 PR의 장비 보고는 테스트 장비가 서버의 동일한 처리기를 호출한다. 관리자 대리 조작 범위는 별도로 합의한다.

## DB 구조

| 테이블 | 주요 컬럼 | 역할 |
| --- | --- | --- |
| `mission_runs` | `id`, `mission_id`, `mission_version`, `mission_snapshot`(JSON), `garden_id`, `device_id`, `requested_by`, `state`, `prepare_key`, `request_hash`, `created_at`, `started_at`, `ended_at`, `last_report_at`, `released_at` | 한 번의 준비와 실행을 기록한다. 미션 스냅샷에 지점 순서·관수 조건 등 당시 내용을 보관한다. 좌표 필드는 미션 저장 계약을 따르며 실내 좌표 형식은 여기서 확정하지 않는다. |
| `device_commands` | `id`, `run_id`, `device_id`, `type`, `status`, `request_key`, `request_hash`, `payload`(JSON), `requested_at`, `sent_at`, `expires_at`, `confirmed_at`, `reason` | 장비에 보낼 명령과 응답 상태를 저장한다. 재전송할 때 같은 명령 ID를 사용한다. |
| `device_reports` | `id`, `device_id`, `message_id`, `run_id`, `command_id`(명령 응답인 경우), `type`, `payload`(JSON), `received_at` | 수신 보고와 결과를 보관한다. 장비·메시지 ID의 조합으로 중복을 구분한다. |

- 준비 요청은 `(requested_by, prepare_key)`, 명령 요청은 `(run_id, request_key)`, 장비 보고는 `(device_id, message_id)`에 고유 제약을 둔다. 같은 키의 같은 요청은 기존 결과를 반환하고, 입력이 다르면 `409`로 응답한다.
- 장비당 미해결 회차는 하나만 허용한다. `released_at`이 비어 있을 때만 `device_id`를 값으로 갖는 생성 컬럼에 고유 인덱스를 둔다. 준비 회차와 명령 저장은 하나의 DB 트랜잭션에서 처리한다. [MySQL 고유 인덱스와 NULL](https://dev.mysql.com/doc/refman/8.4/en/create-index.html)
- 회차 상태 판단과 명령 등록은 같은 회차 행을 잠근 트랜잭션에서 처리한다. 시작 요청이 여러 번 들어와도 첫 `START` 명령을 재사용한다. 장비 전송은 저장이 끝난 뒤 진행하며, 재전송 시 장비도 같은 명령 ID를 중복 처리하지 않도록 실제 통신 계약에 포함한다. [MySQL 잠금 읽기](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

## 작업 상태 전이

**회차 상태**는 장비가 마지막으로 확인한 작업 단계다. **명령 상태**는 서버에 기록된 요청의 진행 상황이다. 예를 들어 회차가 `RUNNING`이고 일시정지 명령의 상태가 `ACKED`라면, 화면에는 **실행 중 / 일시정지 확인 대기**를 표시한다.

| 현재 회차 | 사건 | 다음 회차·표시 |
| --- | --- | --- |
| 없음 | 준비 요청이 저장됨 | `PREPARING` · 준비 응답 대기 |
| `PREPARING` | 해당 명령의 준비 수락 또는 거부를 수신 | 수락이면 `READY`, 거부면 `PREPARE_REJECTED`와 사유 |
| `PREPARING` 또는 `READY` | 시작 전 준비 취소 요청 | 기존 회차 상태를 유지하면서 취소 확인 대기. 이후 시작을 막고 이전 준비 응답은 상태에 적용하지 않는다. 취소 확인을 받으면 `CANCELED` |
| `READY` | 시작 요청 저장 후 장비가 실제 시작을 보고 | 확인 전은 시작 대기, 확인 후 `RUNNING` |
| `RUNNING` | 일시정지 명령 이후 장비가 정지 상태를 보고 | `PAUSED` |
| 시작 요청 이후 | 종료 명령 이후 장비가 정지와 작업 종료를 보고 | `STOPPED` · 작업 종료 |
| `RUNNING` | 같은 회차의 정상 완료 결과를 수신 | `COMPLETED` · 정상 완료 |
| 명령 응답 대기 중 | 기한까지 필요한 응답이 없음 | 마지막 회차 상태 유지. 명령은 `TIMED_OUT`, 화면에는 응답 미확인 |

명령은 `QUEUED → SENT → ACKED → CONFIRMED`로 진행한다. 장비가 ACK를 보내지 않고 곧바로 최종 결과를 보내는 테스트도 허용한다. 거부는 `REJECTED`와 사유로 저장한다. `ACKED`는 수신 확인이며, 준비·시작·정지·완료에는 각각 해당 결과가 필요하다.

시작과 취소가 동시에 오면 이 상태 검사를 한 번에 하나씩 통과시킨다. 취소가 먼저 접수되면 시작을 막는다. 먼저 시작 명령이 만들어졌다면 이후에는 종료 요청으로 다룬다. 취소 요청에 앞선 준비 명령은 무효 처리한다. 늦은 보고는 기록하고, 이미 수신한 메시지 ID는 기존 기록으로 처리한다. 둘 다 취소된 회차를 다시 준비 완료 상태로 바꾸지 않는다. 장비가 준비 거부·취소·종료·정상 완료를 확인하면 `released_at`을 기록한다. 무응답이면 장비를 계속 점유하고, 이후 일치하는 장비 상태 보고로 확인한 뒤 해제한다.

## 테스트 메시지

명령과 보고에는 `deviceId`와 `runId`를 포함한다. 명령 응답에는 `commandId`를 붙여 어느 요청에 대한 응답인지 연결한다. 독립적으로 들어오는 장비 상태·결과에도 고유 `messageId`를 사용한다.

```json
{
  "messageId": "report-42-1",
  "deviceId": "ROVEN-01",
  "runId": 42,
  "commandId": "cmd-42-1",
  "type": "PREPARE_READY"
}
```

첫 PR에서는 장비 송신 인터페이스에 테스트용 구현을 붙인다. 테스트에서 ACK, 준비 수락·거부, 취소 확인을 원하는 순서로 전달하거나 응답을 생략한다. 수신 처리는 메시지 중복, 장비·회차·명령 ID 일치 여부, 현재 회차에서 허용되는 상태 전이를 검사한다.

## 첫 PR 확인 기준

- [ ] 저장된 테스트 미션으로 준비 요청을 보내면 회차와 `PREPARE` 명령이 함께 저장되고 조회된다.
- [ ] ACK만 받으면 준비 대기 상태이고, 수락·거부를 받으면 각각 준비 완료·준비 거부가 표시된다.
- [ ] 응답을 보내지 않으면 무응답으로 표시되고 자동으로 준비 완료되거나 장비 사용이 해제되지 않는다.
- [ ] 준비 취소 확인 후 늦은 수락, 같은 메시지의 중복 수신, 다른 장비의 응답이 상태를 바꾸지 않는다.
- [ ] 같은 요청의 재시도는 회차를 추가하지 않으며, 같은 장비의 동시 준비 요청은 하나만 허용한다.
- [ ] 다른 운영자의 정원·회차에 접근할 수 없다.

후속 구현의 완료 기준에는 동시 시작 요청이 `START` 명령을 하나만 만드는지, 시작·일시정지·종료 중 응답이 끊겨도 실제 상태와 정상 완료를 추정하지 않는지가 포함된다.

## 구현 전에 합의할 항목

1. 미션 저장 담당자와 `missionId`, `version`, 미션 스냅샷에 담을 항목을 맞춘다.
2. FE 담당자와 상태 조회 시점, 준비·취소 버튼 활성 조건, 응답 미확인 문구를 맞춘다.
3. 장비팀과 실제 통신 방식, 응답 기한, 중복 명령·늦은 보고 처리, 무응답 뒤 안전하게 상태를 확인하는 절차를 정한다.
