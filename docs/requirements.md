## 2. 첫 데모 시나리오

운영자가 대시보드에서 **UGV-01의 고정 경로 주행 시작**을 누른다. 화면에 실행 ID가 나타나고, 경로 `A(0,0) → B(10,0) → C(10,5)` 위에서 차량 표시가 이동한다. 시작 직후 A에서 진행률 0%를 표시하고 약 3초에 B에서 50%, 약 6초에 C에서 100%와 완료 상태를 표시한다. 완료 후 페이지를 새로고침하면 같은 실행 ID와 최종 위치가 다시 표시된다.

좌표는 현장 좌표와 독립된 모의 평면의 미터 단위다. BE가 저장한 시작 시각을 기준으로 서버에서 상태와 위치를 계산한다. 체크포인트 사이 위치는 선형 보간하고, 진행률은 경과 시간 기준으로 계산한다. FE는 약 1초마다 서버 상태를 조회한다. 첫 데모는 차량 한 대, 경로 하나, 실행 시작·조회·결과 복구를 다룬다. 실차 연동, GPS 지도, 경로 편집, 충돌 판단, 중지·재개, 다중 차량은 후속 범위로 둔다.

## 3. API와 데이터 계약 제안

| 요청 | 정상 결과 | 합의할 예외 |
| --- | --- | --- |
| `POST /simulation-runs` · JSON `{"vehicle_id":"UGV-01","route_id":"demo-route-v1"}` | `201`과 생성된 실행 스냅샷 | 지원하지 않는 차량·경로 `422`, 같은 차량에 진행 중인 실행이 있으면 `409`와 기존 실행 ID |
| `GET /simulation-runs/{run_id}` | `200`과 해당 실행 스냅샷 | 존재하지 않는 ID `404` |

스냅샷 예시

```json
{
  "id": 42,
  "vehicle_id": "UGV-01",
  "route_id": "demo-route-v1",
  "status": "running",
  "progress_percent": 50,
  "position": {"x_m": 10, "y_m": 0},
  "waypoints": [{"x_m": 0, "y_m": 0}, {"x_m": 10, "y_m": 0}, {"x_m": 10, "y_m": 5}],
  "started_at": "2026-11-13T05:00:00Z",
  "completed_at": null
}
```

- 상태는 `running`과 `completed`로 제안한다. 완료 후 조회는 끝점과 100%를 반환한다. 시간은 UTC ISO 8601, ID는 정수, 진행률은 0~100의 정수다.
- BE는 실행 ID, 차량 ID, 경로 버전, 시작 시각을 DB에 보관한다. 첫 버전은 고정 시간표로 최종 위치와 완료 시각을 재계산하는 방식을 제안한다. 프로세스가 바뀌어도 같은 실행을 조회할 수 있도록 상태 계산은 요청을 처리하는 인스턴스에 독립적이어야 한다.
- FE는 성공 응답의 ID를 페이지 URL에 기록하고, URL에 ID가 있으면 단건 조회로 복구한다. 진행 중에는 시작 버튼을 비활성화한다. `409` 응답에서도 기존 ID로 복구할 수 있도록 오류 JSON 형식을 FE와 BE가 합의한다.

## 4. 작업 배정과 의존관계

| 역할 | 첫 작업 | 완료 증거 및 의존관계 |
| --- | --- | --- |
| PM | 시나리오, 상태 전이, API 예시, 데모 기준을 검토하고 버전을 확정한다. | FE·BE가 동일한 응답 예시를 사용하고, Infra가 검증 환경을 지정한다. |
| BE | 실행 모델, 생성·단건 조회, 시간 기반 위치 계산, 중복 실행 방지, 계약 테스트를 구현한다. | SQLite에서 시작·중간·완료·404·409를 재현한다. FE와 성공·오류 형식 합의 후 구현한다. |
| FE | 고정 경로와 차량 위치, 시작 버튼, 진행률·상태, 새로고침 복구, 오류 표시를 구현한다. | 계약 예시를 이용해 모의 응답으로 먼저 확인하고, 이후 로컬 BE 및 데모 API에 연결한다. |
| Infra | 실제 데모 환경, FE→BE 연결, Cloud SQL 접근, 시크릿 주입, 배포 증거 수집 방법을 점검한다. | 환경 점검은 병렬 진행한다. 승인 후 FE·BE CI와 동일 버전의 배포를 확인하고, 리비전·커밋·실행 ID를 공유한다. |

작업 순서는 PM과 FE·BE의 계약 합의 → FE·BE 병렬 작업 및 Infra 환경 점검 → 로컬 연동 → 데모 환경 검증이다.

## 5. 데모 통과 기준 및 검증 절차

| 순서 | 검증 | 통과 기준 |
| --- | --- | --- |
| 1 | 로컬 BE 테스트와 FE lint·build 실행 | 기존 Todo 테스트와 신규 실행 계약 테스트 통과. BE 테스트는 시간을 제어해 0·3·6초의 상태와 위치를 확인한다. |
| 2 | 지정된 환경에서 대시보드 접속 후 주행 시작 | 브라우저 네트워크에서 `POST` 201과 생성 ID 확인. 화면이 시작 직후 실행 중 상태를 표시한다. |
| 3 | 완료까지 관찰 | 폴링 응답의 위치와 화면 표시가 일치한다. 경로 중간의 진행률 변화를 관찰하고, 정상 네트워크에서 생성 후 8초 이내에 C·100%·완료가 표시된다. |
| 4 | 완료 화면 새로고침 | 동일한 ID에 대한 `GET` 200과 동일한 완료 상태·위치를 확인한다. 새 `POST`가 발생하지 않는다. |
| 5 | 오류 및 배포 확인 | 존재하지 않는 ID는 404와 화면 오류 메시지를 표시한다. 데모 환경에서 실행 ID와 함께 CI 결과, FE·BE 리비전, DB 영속성 확인 증거를 남긴다. |

Cloud SQL 영속성은 새로고침과 별도로, 같은 DB에 연결된 새 BE 프로세스에서 동일 실행을 조회하거나 테스트 DB에서 해당 실행 레코드를 확인한다. 로컬 SQLite 검증은 별도로 기록한다.
